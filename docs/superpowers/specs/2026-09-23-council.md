# План расширения: «Совет при акиме» — мультиагентное обсуждение плана

**Цель:** после «Разбора партии» пользователь выносит план на заседание совета. Семь AI-участников, каждый из которых отвечает за одно слагаемое формулы Score, обсуждают план на цифрах движка: предлагают поправки, возражают друг другу и голосуют. Председатель собирает пакет поправок, проверяет его движком и пишет протокол. Пользователь принимает поправку, план меняется, открывается новый разбор.

**Почему это не декорация:** Score — это компромисс между пятью направлениями, худшим районом и штрафами за значения ниже 40. Совет «раскладывает» формулу на людей: у каждого участника своё слагаемое и своя метрика. Спор возникает из реальных противоречий в данных, а не из промпта. Например, в плане из датасета все сходятся, что M5 в Сарыарке — слабый ход, но расходятся в том, на что его заменить (см. пример ниже).

**Принцип разделения:** цифры считает движок, позицию определяют правила, слова пишет LLM, каждую поправку и каждое число проверяет движок.

**Опирается на v1:** `SimulationService` (validate, evaluate, review, замены), `LlmClient`, офлайн-режим и фактчек чисел из трека C, экран «Разбор партии».

## Участники

Персонажи вымышленные: только должности, без имён реальных людей. В интерфейсе это подписано.

| Участник                               | Слагаемое формулы                           | Метрика (чем больше, тем лучше)                     | Характер                             |
| -------------------------------------- | ------------------------------------------- | --------------------------------------------------- | ------------------------------------ |
| 🚌 Заместитель акима по транспорту     | T1, T2 (вес 0.20)                           | вклад направления в средний балл города             | прагматик-инженер                    |
| 🌳 Заместитель по экологии             | E1, E2 (0.20)                               | то же для экологии                                  | эмоциональный, думает о зиме и смоге |
| 🏫 Заместитель по социальной сфере     | S1, S2 (0.22)                               | то же для соцсферы                                  | говорит о детях и очередях           |
| 🛡️ Заместитель по безопасности         | B1, B2 (0.18)                               | то же для безопасности                              | сухой, оперирует рисками             |
| 🔧 Заместитель по городскому хозяйству | C1, C2 (0.20)                               | то же для сервисов                                  | «лишь бы не прорвало трубы»          |
| 🏘️ Омбудсмен районов                   | 0.3 × худший район и штраф за значения < 40 | худший балл района минус число критических значений | голос Нуры и отстающих               |
| 💰 Руководитель управления финансов    | бюджет                                      | прирост Score на 10 единиц бюджета                  | считает каждую единицу               |
| ⚖️ Председатель совета                 | итоговый Score                              | —                                                   | нейтральный, подводит итог           |

Вклад направления в средний балл = Σ по районам (доля населения × Σ вес × значение показателей направления). Сумма пяти вкладов равна среднему баллу города, это проверяется тестом.

## Ход заседания

1. **Подготовка (движок, без LLM).** Для каждого участника строится бриф:
   - метрика до и после плана;
   - свои критические (< 40) и пограничные (40–42) значения;
   - вклад мер своего направления;
   - позиция по правилам (за, условно, против);
   - до трёх кандидатов-поправок: одиночные замены, которые не снижают Score и улучшают метрику участника больше чем на 0.01, отсортированные по его метрике;
   - список «разрешённых чисел» для фактчека.
2. **Раунд 1 — выступления.** Семь LLM-вызовов параллельно, таймаут 12 с на каждый. Ответ — JSON `{ speech, amendmentId | null }`, до 60 слов. Позиция задана брифом, LLM её формулирует и обосновывает.
3. **Проверка каждой реплики.** `amendmentId` должен быть из списка кандидатов, все числа в тексте — из брифа. Если нет, для этого участника подставляется шаблонная реплика, остальные не страдают.
4. **Лидирующая поправка и возражения (движок).** Лидер — поправка с наибольшим приростом Score. Для неё считается, как изменится метрика каждого участника. Кто теряет 0.1 и больше, тот возражает.
5. **Раунд 2 — спор.** До двух возражений и ответ автора лидирующей поправки. Сначала возражения параллельно, затем ответ.
6. **Председатель (агент с инструментами, до 4 шагов).** Инструменты:
   - `evaluate_package(amendmentIds)` — движок проверяет пакет из нескольких поправок: допустимость, стоимость, Score;
   - `get_amendment_impacts(amendmentId)` — кто выигрывает и кто теряет.

   Итог — протокол в JSON:
   - решение: принять, принять с поправками или доработать;
   - рекомендованный пакет (только проверенный движком);
   - компромиссы с ценой в баллах;
   - особые мнения.

7. **Голосование по рекомендации председателя (правила, без LLM).** Метрика участника не снизилась — «за»; снизилась меньше чем на 0.1 — «воздержался»; снизилась на 0.1 и больше или новое значение < 40 в его зоне — «против».
8. **Действие пользователя.** «Принять поправку» или «Принять пакет»: план меняется, запускается новый разбор, протокол сохраняется.

## Эталон: заседание по плану из датасета

План M7@Нура, M8@Нура, M10@Нура, M12, M5@Сарыарка: Score 56.54, стоимость 95. Все числа ниже посчитаны по правилам этого документа; их можно использовать как ожидаемые значения в тестах.

- **Общая цель атаки — M5@Сарыарка:** вклад 0.17 за 25 единиц. Это 0.007 балла на единицу против 0.06–0.07 у школы и поликлиники в Нуре.
- **Поправки раунда 1:**

| Участник     | Поправка                           | Score | ΔScore | Стоимость | Своя метрика                       |
| ------------ | ---------------------------------- | ----- | ------ | --------- | ---------------------------------- |
| Омбудсмен    | M5@Сарыарка → M3@Нура              | 57.21 | +0.66  | 100       | +2.02 (худший район 52.96 → 54.98) |
| Безопасность | M5@Сарыарка → M2                   | 56.88 | +0.33  | 92        | +0.20                              |
| Экология     | M5@Сарыарка → M6                   | 56.76 | +0.22  | 90        | +0.20                              |
| Транспорт    | M5@Сарыарка → M3@Есиль             | 56.76 | +0.21  | 100       | +0.49                              |
| Финансы      | M5@Сарыарка → M11@Нура             | 56.69 | +0.15  | 80        | +0.10                              |
| Хозяйство    | M10@Нура → M14                     | 56.64 | +0.08  | 99        | +0.61                              |
| Соцсфера     | — (поддерживает план без поправок) |       |        |           |                                    |

- **Мини-спор «ЛРТ — да, но где?»:** транспорту выгоднее ЛРТ в Есиле (своя метрика +0.49 против +0.29), а городу — в Нуре (+0.66 против +0.21).
- **Лидирующая поправка — ЛРТ в Нуре.** Экология теряет 0.16: E2 Сарыарки возвращается с 48.75 ровно на 40.00. Формально это ещё не критично (штраф только за < 40), но до штрафа ноль запаса. Экология возражает, омбудсмен отвечает: Нура — худший район, а на худший район приходится 30% итога.
- **Председатель проверяет пакеты:**
  - ЛРТ в Нуре + M14 вместо M10 — стоимость 104 > 100, движок отклоняет;
  - безопасность + хозяйство — допустимо, но 56.96 < 57.21.

  Рекомендация: одна поправка, ЛРТ в Нуре, Score 57.21, до оптимума 0.03. Компромиссный вариант — M6 (+0.22), он сохраняет экологическую меру. Цена экологии — 0.44 балла. Отдельно председатель отмечает: экономия, которую предлагают финансы, по правилам кейса баллов не даёт.

- **Голосование: 5 за, 1 воздержался, 1 против.**
  - За: транспорт +0.29, омбудсмен +2.02, финансы +0.045, соцсфера 0, безопасность 0.
  - Воздержался: хозяйство −0.05.
  - Против: экология −0.16 (особое мнение в протоколе).

## Архитектура

### API: модуль `apps/api/src/council/`

| Файл                        | Ответственность                                                                                 |
| --------------------------- | ----------------------------------------------------------------------------------------------- |
| `types.ts`                  | `CouncilRoleId`, `Brief`, `Amendment`, `CouncilEvent`, `Protocol`                               |
| `roles.ts`                  | 7 участников и председатель: заголовок, эмодзи, метрика, характер                               |
| `metrics.ts`                | метрики участников по `Evaluation`                                                              |
| `amendments.ts`             | кандидаты для роли, влияние поправки на всех, `evaluatePackage` через валидацию и оценку движка |
| `briefs.ts`                 | бриф участника: факты, позиция, кандидаты, разрешённые числа                                    |
| `votes.ts`                  | правила голосования                                                                             |
| `deputy-agent.ts`           | одна реплика: промпт → JSON → проверка → при ошибке шаблон                                      |
| `chair-agent.ts`            | цикл инструментов председателя и протокол                                                       |
| `offline-council.ts`        | шаблонные реплики и протокол из тех же брифов                                                   |
| `council-orchestrator.ts`   | раунды, параллельность (`Promise.allSettled`), таймауты, поток событий                          |
| `council-session.entity.ts` | сохранение сессии в PostgreSQL (plan, events, protocol в jsonb) и миграция                      |
| `council.controller.ts`     | HTTP и SSE                                                                                      |

События (`CouncilEvent`), один и тот же тип в API и вебе:

```ts
type CouncilEvent =
  | { type: 'opened'; plan: Plan; score: number; members: CouncilMember[] }
  | {
      type: 'speech';
      round: 1 | 2;
      roleId: CouncilRoleId;
      stance: Stance;
      text: string;
      amendmentId: string | null;
      source: 'llm' | 'offline';
      verified: boolean;
    }
  | { type: 'amendment'; amendment: Amendment } // scoreAfter, delta, cost, impacts по всем ролям
  | {
      type: 'objection';
      roleId: CouncilRoleId;
      amendmentId: string;
      text: string;
    }
  | {
      type: 'package-check';
      amendmentIds: string[];
      valid: boolean;
      score?: number;
      reason?: string;
    }
  | {
      type: 'votes';
      votes: {
        roleId: CouncilRoleId;
        vote: 'for' | 'abstain' | 'against';
        delta: number;
      }[];
    }
  | { type: 'protocol'; protocol: Protocol }
  | { type: 'closed' }
  | { type: 'failed'; message: string };
```

Событие `package-check` показывает в UI попытки председателя, в том числе отклонённые движком. Это наглядное доказательство, что AI не может обойти правила.

HTTP:

| Метод | Путь                               | Ответ                                                                        |
| ----- | ---------------------------------- | ---------------------------------------------------------------------------- |
| POST  | `/api/council/sessions`            | `{ plan }` → `{ sessionId }`; невалидный план → `422`; заседание идёт в фоне |
| GET   | `/api/council/sessions/:id/events` | SSE: события по мере готовности; поздний подписчик получает всё с начала     |
| GET   | `/api/council/sessions/:id`        | сохранённая сессия целиком (повторный показ, запасной вариант для демо)      |

- SSE в Nest: `@Sse()` возвращает `Observable<MessageEvent>`. Сессия держит `ReplaySubject`, `rxjs` уже есть в зависимостях.
- В браузере — `EventSource`. В тестах он подменяется фейком.
- Проверить в первые 15 минут, что Vite proxy отдаёт SSE без буферизации и в Compose, и локально.

### Промпты

Участник (system):

> Ты — {должность} на заседании совета при акиме (вымышленный персонаж). Твоя зона — {слагаемое формулы}. Характер: {характер}. Правила: используй только числа из блока ФАКТЫ, ничего не считай сам; твоя позиция уже определена — «{позиция}», обоснуй её; поправку выбирай только из списка КАНДИДАТЫ по id или не предлагай; до 60 слов, живая речь без канцелярита. Ответ — JSON `{"speech": string, "amendmentId": string | null}`.

В user-сообщении — ФАКТЫ, КАНДИДАТЫ и план в JSON.

Председатель получает все реплики, поправки с влиянием и инструменты. Правила:

- называть цену каждого компромисса в баллах;
- рекомендовать только пакеты, которые вернули `valid: true`;
- ответ — JSON протокола.

### Модели и переменные

- Участники — быстрая модель (`AI_COUNCIL_MODEL`), председатель — основная (`AI_MODEL`). Если `AI_COUNCIL_MODEL` пустая, используется `AI_MODEL`.
- `AI_COUNCIL_TIMEOUT_MS=12000` — таймаут реплики.
- Всё добавить в `.env.example` с комментариями.
- Нагрузка: около 11 вызовов на заседание (7 + до 3 + председатель), 3–4 последовательных этапа, 15–25 с при быстрой модели.

### Веб: `apps/web/src/features/council/`

- Кнопка «Вынести на совет» на экране разбора.
- `CouncilTable` — круглый стол: 7 мест и председатель, подсветка говорящего, чип позиции, бейдж «✓ цифры подтверждены движком».
- `SpeechFeed` — лента реплик по раундам с меткой «AI» или «шаблон».
- `AmendmentBoard` — карточки поправок: Score, Δ, стоимость, мини-столбики «кто выигрывает и кто теряет» по семи метрикам, кнопка «Принять» (меняет план и запускает новый разбор).
- `PackageLog` — попытки председателя, отклонённые пакеты с причиной.
- `VoteBar` и `ProtocolCard` — голосование, решение, компромиссы с ценой, особые мнения.
- Если есть карта: поправки — стрелки между районами, возражения — подсветка задетых районов.

## Тесты

- `metrics`: сумма пяти вкладов равна среднему баллу; значения для примера из датасета.
- `amendments`: кандидаты и лидер для примера (таблица выше); пакет «ЛРТ в Нуре + M14 вместо M10» отклоняется со стоимостью 104.
- `votes`: 5 / 1 / 1 для примера.
- `deputy-agent` с фейковым `LlmClient`: корректный ответ; `amendmentId` не из списка; число не из брифа; битый JSON; таймаут. Во всех ошибочных случаях — шаблон только для этого участника.
- `chair-agent`: отклонённый движком пакет попадает в `package-check` и не попадает в рекомендацию; превышение числа шагов → офлайн-протокол.
- `council-orchestrator`: порядок событий; падение всех LLM-вызовов даёт полностью офлайн-заседание с тем же составом событий.
- `council.controller`: поздний подписчик получает все события; неизвестная сессия → `404`; невалидный план → `422`.
- Веб: отрисовка из фикстуры событий; «Принять» вызывает новый разбор с изменённым планом.

| 0:45–1:45 | агент-участник, офлайн, оркестратор + тесты с фейковым LLM    | карточки поправок, голосование, протокол |

Полная версия — около 2.5 часа на двоих.

**Облегчённая версия (около 1 часа)** на случай нехватки времени:

- на заседание вызываются три участника, которых план задевает сильнее всего: самый большой плюс и два самых больших минуса метрики;
- один раунд, без возражений;
- пакет подбирает движок, председатель только формулирует;
- без SSE: один POST возвращает всё заседание, интерфейс проигрывает его по репликам;
- без хранения в БД.

## Что резать (с начала списка)

1. Раунд 2 (возражения): конфликт показывает председатель.
2. Хранение сессий в PostgreSQL: держать в памяти.
3. SSE: один POST, интерфейс проигрывает заседание с анимацией.
4. Инструменты председателя: пакет подбирает движок.

Не резать: брифы из движка, проверку поправок и чисел, офлайн-режим, кнопку «Принять поправку».
