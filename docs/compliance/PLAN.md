## Формат обязательной разметки

Одна строка на одно проверяемое требование. Обязательные поля:

`ID → точный источник/версия/пункт → требование → применимость → статус → код/документ → проверка → результат/артефакт/SHA → пробел → ответственный → срок`.

Группы ID: `RULE-5.x`, `CASE-*`, `DATA-*`, `SOURCE-*`, `HOUR-*`, `DEMO-*`, `SUBMIT-*`.
Составные пункты дробить, например `RULE-5.4.15-env`, `RULE-5.4.15-install`, `RULE-5.4.15-core-check`.
Сохранять обратную связь с родительским пунктом и полный исходный текст.

Статусы: `подтверждено`, `частично`, `не реализовано`, `не проверено`, `внешнее подтверждение`, `неприменимо с причиной`.
Назначение роли ниже предварительное; конкретного человека фиксирует команда.
«Подтверждено» допустимо только с проверяемым свидетельством; тестовый файл без результата запуска даёт статус «не проверено».
Правила организатора, необязательные возможности и будущие этапы не превращать автоматически в обязательные продуктовые функции.

## Последовательность работ

### P0 — допуск и доказательства, до сдачи

1. **Закрепить источники.** Капитан предоставляет опубликованное ТЗ выбранного кейса, его версию, полный комплект подачи, официальный старт, часовой пояс окончания 18:00 и подтверждение выданного репозитория. Сохранить разрешённую копию/ссылку, дату и происхождение. Не подменять ТЗ внутренним датасетом или README. До получения источника критерии кейса помечать предварительными.
2. **Разложить всё положение.** Дополнить RULES_MAP атомарными строками: требования 5.1–5.2; каждое событие расписания 5.3; материалы, происхождение, история и запуск 5.4; критерии/проверки 5.5–5.6; пять критериев Demo Day 5.7; условия призов 5.8; каждое основание 5.9.2; обращения и исключения 5.10. Для каждого указать применимость, владельца и свидетельство либо конкретный пробел. Организационные подтверждения хранить без публикации персональных номеров/телефонов/документов.
3. **Раскрыть происхождение.** Ответственный за документацию расширяет EXTERNAL_TOOLS либо создаёт SOURCES: компонент, точная версия/commit, автор/источник, лицензия/условия, использованные пути, внесённые изменения, готовность до старта, роль AI. Включить npm-зависимости, модели/API, синтетический датасет и его автора/источник, предоставленные дизайны, изображения/шрифты, шаблоны и инфраструктуру. Lockfile помогает инвентаризации, но не заменяет раскрытие остальных материалов. Не придумывать лицензии; неопределённость отметить явно.
4. **Собрать почасовую историю.** Ответственный за историю создаёт PROGRESS: интервал по официальному старту → реальный промежуточный результат → SHA/артефакт → участник/вклад. Учитывать дизайн, данные, тесты и архитектуру, а не только merge-коммиты. Git timestamps не доказывают push к дедлайну или присутствие; запросить доступные свидетельства организатора. Не менять даты и не восстанавливать несуществующий прогресс задним числом. Обновить устаревшие утверждения локального BUILD_STORY при согласовании с upstream.
5. **Проверить воспроизводимость.** Ответственный за техническую сдачу на выбранном SHA выполняет README в отдельном чистом окружении без личного `.env`: установка, миграции, запуск, `npm run check`, smoke и Playwright. Использовать отдельную Compose-базу; существующие данные не удалять. Зафиксировать Node/npm/Docker, команды, длительность, exit codes, CI URL и артефакты. Основной путь: пример → 56.54 → замена → 57.21 → офлайн-отчёт → сохранение → реестр после перезагрузки. Проверить ошибочный план и доступность без личных аккаунтов.
6. **Зафиксировать сдачу.** Капитан/технический ответственный создают SUBMISSION: выбранный кейс, полный комплект, SHA, время/часовой пояс, официальный URL репозитория, ссылка демо и подтверждение отправки. Сверить SHA развёртывания с итоговым SHA. После дедлайна не представлять новые изменения как часть зафиксированного результата.

10. **Согласовать документы.** README даёт вход в матрицы, источники, прогресс, запуск и сдачу. Исправить устаревшие сведения о публичном демо.
