# QOL-SIM — пять решений для города

Учебный симулятор для городских управленцев, аналитиков и команд: распределите бюджет и разберите последствия своего плана.

**Мы потратили 86 из 100 единиц бюджета. Город получил 52.45 балла — меньше, чем если бы мы ничего не сделали: 52.56.** В заданной модели безопасные переходы замедлили движение в Алматы, показатель упал ниже критического порога, и город получил штраф. С этого примера удобно начать знакомство с QOL-SIM.

## Как мы до этого дошли

**Сначала выбирали задачу.** Обсуждали финтех и городской кейс. В «Акиме на 5 часов» нас зацепил сам выбор: денег мало, инициатив много, последствия видны не сразу. Хотелось, чтобы человек сам собрал план и увидел, чем пришлось пожертвовать.

**Потом искали, как в это играть.** Саяжан перебирал интерфейсы, спорил с вариантами реализации и выбирал, какие функции строить. Маргулан искал референсы и вместе с нами правил путь пользователя. Дос разбирал кейс, расчёты и агентную логику. Планы отдавали Codex, проверяли результат и двигались дальше. Основное приложение собирал Саяжан.

**Разбор стал похож на разбор шахматной партии.** Пять решений, вклад каждого хода, упущенные возможности и замена, которую можно сразу проверить. Числа считает движок. AI получает результаты и объясняет их. Затем появился совет при акиме: вымышленные участники обсуждают поправки, возражают и голосуют. Пользователь решает, принимать ли рекомендацию.

**Мелочи заставили вернуться к расчётам.** Разность двух округлённых оценок давала +3.98, а точный прирост — +3.99. Исправили передачу результата: теперь API отдельно отдаёт рассчитанный прирост. В макете совета тоже нашли расхождение: замена давала 56.63, а не 56.64. Эти случаи записаны в [дневнике](BUILD_STORY.md#september-23--implementing-the-plan-review-simulator) и закреплены тестами.

**Пока приложение собиралось, мы искали, кому его показать.** Дос подготовил поиск контактов и порядок обращений. Маргулан писал людям, снимал видео и вёл журнал. Хотели выйти с работающим примером и конкретным вопросом к тем, кто занимается городами или обучает управленцев.

Это последовательность работы, восстановленная командой. Этапы пересекались; точного почасового хронометража мы не приписываем. Ранние записи и технические подробности сохранены в [BUILD_STORY.md](BUILD_STORY.md).

## Попробовать за две минуты

1. Пройдите или пропустите обучение. В Нуре школы имеют показатель **38**, медицина — **35**. Оба ниже критической отметки 40.
2. Загрузите **план-ловушку** и разберите его: бюджет **86**, Score **52.45**, ниже бездействия **52.56**.
3. Откройте **пример плана**: школа, поликлиника и освещение в Нуре; цифровая платформа по городу; чистое топливо в Сарыарке. Бюджет **95**, Score **56.54**, место **566 из 694 395**.
4. Примените замену **M5 в Сарыарке → M3 в Нуре**. Новый Score — **57.21**. Глобальный оптимум модели — **57.24**.
5. Откройте **совет при акиме**. Запустите заседание, прочитайте возражения и протокол. Принятие рекомендации меняет план и запускает новый разбор. Заседание сохраняется для повторного просмотра.
6. Отправьте план в реестр команд. Сервер пересчитает результат; в таблице останется лучший результат команды.

## Запуск

Нужен Docker с Compose v2. Из корня репозитория:

```sh
cp .env.example .env
docker compose up --build --wait --wait-timeout 180
```

Откройте [localhost:5173](http://localhost:5173). API: [localhost:3000/api/scenario](http://localhost:3000/api/scenario). Compose выполняет миграции перед запуском API; движок один раз готовит пространство допустимых планов. PostgreSQL хранит результаты команд и заседания.

**Без AI-ключа работают расчёты, разбор и совет на явно обозначенных шаблонах.** Для ответов модели задайте серверный `OPENAI_API_KEY` в `.env` и пересоберите API: `docker compose up -d --build api`. При сбое модели затронутый ответ заменяется шаблоном; его источник виден в интерфейсе. Проверка с настоящим ключом в доступных записях не подтверждена.

```sh
# Проверить работающий стек без установки Node на хост:
docker compose exec -T web node scripts/smoke.mjs http://localhost:5173 http://api:3000
docker compose logs -f
docker compose down  # Сохраняет данные PostgreSQL
```

Порты по умолчанию — 5173, 3000 и 5432; настройки находятся в `.env.example`. Пароль базы в примере предназначен для локальной разработки. Compose запускает серверы разработки и привязывает порты к localhost. [Локальный Node, все переменные, API, миграции и развёртывание](docs/DEVELOPMENT.md).

## Как считается результат

Всем доступен бюджет **100**, пять районов и **14 мер** по пяти направлениям. Нужно выбрать **ровно пять разных мер**, максимум две из одного направления. Охватывать все пять направлений не требуется. Для районной меры нужен район, для городской он не указывается. M1/M3 несовместимы везде; M4/M7 и M5/M13 — в одном районе. Невалидный план получает причины отказа, без Score.

```text
Эффект меры = полный эффект × (8 − лаг) / 8
Показатель = clip(исходное значение + эффекты + синергии, 0, 100)
D[район] = сумма показателей с весами
D_avg = среднее D с учётом долей населения
Score = 0.7 × D_avg + 0.3 × min(D) − N_crit
N_crit = число пар «район × показатель» со значением строго ниже 40
```

Score — это **Astana Quality of Life Score** из задания. Горизонт — восемь кварталов. Синергии фиксированы. Остаток бюджета бонуса не даёт. Вклад хода рассчитывается по Шепли: учитывает взаимодействие с остальными решениями. Ранг получаем полным перебором допустимых планов. [Датасет, веса и каталог](docs/data/astana-dataset.md); [подробности расчёта и оценок ходов](docs/SIMULATOR.md#как-считается-результат).

## Архитектура

```text
React / Vite → NestJS → TypeScript-движок → Score, вклад, ранг, замены
                     → инструменты движка → AI-аналитик / офлайн-разбор
                     → совет → события, голосование, протокол
                     → TypeORM / PostgreSQL → реестр и история заседаний
```

Стек: React 19, Vite 8, NestJS 12, TypeScript 5.9, TypeORM 0.3, PostgreSQL 17. Числа, ограничения и допустимые замены принадлежат движку. Аналитик вызывает его инструменты: до шести шагов, по умолчанию до 25 секунд. Совет сохраняет события до отправки через SSE, поддерживает переподключение и просмотр записи.

Модель формулирует объяснения и реплики. Проверки структуры, ID и чисел отсекают часть ошибок, но не доказывают смысловую верность каждого утверждения. Ключ хранится на сервере. [Компоненты, инструменты агента и устройство совета](docs/SIMULATOR.md).

## Что осталось открытым

- Данные синтетические, карта схематическая. Оценка показывает последствия внутри заданной модели; точность прогноза для настоящего города не проверена.
- Реестр без авторизации: название команды — открытая метка. Сервер рассчитан на один API-процесс.
- Самообучение, NPC-соперники и неожиданные события остались идеями.
- Отдельный агентный runtime Builder 2 передан через [draft PR #22](https://github.com/BAITC-Hacks/hack-b0e0ddb6-t-sting/pull/22). На момент этой редакции он не включён в основной сценарий; интеграция с модулем Builder 1 не подтверждена. Описанный выше продукт работает на текущем движке `astana-v1`.

Происхождение внешних инструментов и рекомендаций для разработки — в [EXTERNAL_TOOLS.md](docs/EXTERNAL_TOOLS.md). Codex помогал писать код и редактировать текст. Выбор задачи, функций и проверка результата — работа команды.
